# v0.2.1 — content_type-based Upload Validation

## Breaking Changes

- **`accepts` removed from the upload session config** — MIME enforcement now rests solely on the target bucket's `accepts` list, validated against the declared `content_type`.
  - Requests that still send `accepts` are rejected (`400`, unknown fields are not allowed).
  - **Uploads without a bucket now require `content_type`** (`400 content_type is required when bucket is not provided`). At upload completion the declared type is verified against the MIME type inferred from the file's extension; a mismatch rejects the upload and removes the temporary file.
  - The per-session output-type checks for image processing (`compressed/transformed output type '...' is not accepted`) are gone. Bucket uploads remain covered: the rewritten output `content_type` is validated against the bucket's `accepts` at session creation, and no-bucket uploads must still declare an `image/*` `content_type` for `image_compression` / `image_transformation`.
- **In-flight resumable sessions from v0.2.0 or older fail after this upgrade** — session tokens embed the upload config, which no longer deserializes. Recreate those sessions.

## Upgrade Notes

- No action needed for normal clients that never sent `accepts`. Clients that did must switch to a bucket with an `accepts` list (validated against `content_type`), or to declaring `content_type` directly.

## Documentation

- `api/upload` rewritten around `content_type` (field table, validation rules, no-bucket section, error table).
- Quick start's no-bucket example now declares `content_type`.
- MIME validation docs gained an "Uploads Without a Bucket" section.
